# AGENTS.md — read this before working in this repo

**Project:** UmDatathon 2026. A 10,000,000-row synthetic SWIFT-like payments file
(`swift_umdac_datathon_2026_fictitious_payment_data.csv`, ~4.95 GB) was generated by a
hidden rule set. Our job: reverse-engineer those rules per feature area ("groups") and
document them with proof. This is a Windows machine; shell is PowerShell; Python packages
install to the user site (duckdb is installed).

## The one rule about the CSV

Never scan it directly. All work happens on the parquet caches in `analysis/`. The only
legit direct uses are the two build scripts and pulling a one-off proof row.

## Directory map

```
analysis/
  cache_full/     20 parts (part_*.parquet) — light columns + derived path features
                  (has_gap, n_vis, half, ...). Built by build_cache.py.
  cache_party/    20 parts — account + DETAILS/TOKENS text columns + ANOMALY_TYPE.
                  Built by build_cache_party.py. Serves g8/g7-type work.
  agg/            cached aggregates (*.pkl) that chart scripts render from.
  groups/<name>/  ONE folder per feature group: README.md (rules, chart explanations,
                  proof rows from the real CSV) + that group's charts.
  _archive/       superseded scripts/charts/pickles. History only — do not read or
                  run anything here unless explicitly asked.
  _common.py      shared paths + helpers (DuckDB connection, glob, rand_sample, savefig)
  build_cache*.py rebuild the caches (only if a new column is needed)
  gN_*.py         group scripts (one entry script per group; g6 has control follow-ups)
groups/README.md  status table of all 8 groups + method conventions
```

## How a group gets done (methodology — apply to every remaining group)

1. One plain question per group. Design the comparison around the suspected mechanism,
   not around "do anomaly rows look different" fishing.
2. Run group-bys/window functions on the FULL 10M rows with DuckDB:
   `duckdb` + `read_parquet('analysis/cache_full/part_*.parquet')` (glob all parts).
   A full group-by is seconds. There is no memory problem.
3. Sampling discipline: random samples (never a `::40` stride — aliasing risk) and ONLY
   for chart shapes. Every number quoted in a README must be exact (full-data count,
   min/max, quantiles). Rare buckets (< a few thousand rows) always exact.
4. Every claim gets a control: compare anomalous vs clean rows holding everything else
   fixed (same corridor, same bank count, ...). Report the clean baseline next to the
   anomaly number. Negative results ("X does not matter") go in the README too.
5. Write `analysis/groups/<name>/README.md`: rules found, dead ends with the numbers
   that killed them, what each chart shows, 2+ real rows from the CSV as proof.
   Charts saved into the group folder via `savefig(fig, "name.png", group="<name>")`.
6. Update the status table in `analysis/groups/README.md`.

## Conventions and gotchas

- Clean rows are `ANOMALY_TYPE IS NULL` (not `''`). Using `= ''` silently matches nothing.
- DuckDB's CSV reader chokes on the embedded quotes/newlines in DETAILS/TOKENS columns —
  that's why `cache_party/` is built with pandas chunking, then queried with DuckDB.
- BIC8 country = characters 5–6 of the bank code. Route paths are `;`-separated with
  `...` placeholders for hidden banks.
- `half` in cache_full is a deterministic 50/50 row split for hold-out validation.
- Time window of the data: 2023-04-30 .. 2023-07-30 (90 days), epoch seconds, UTC.
- If a run fails after writing temp tables, just rerun the script — DuckDB temp tables
  don't persist between processes.

## Token-economy guidance (for AI agents)

- Orient from `groups/*/README.md` first; they contain the findings, so you usually do
  NOT need to read the scripts or rerun anything.
- Read a group's script only to modify its analysis. Don't list `_archive/` contents
  speculatively; it's dead history kept on purpose.
- Never `cat`/sample the raw CSV; caches answer everything and are fast.
- Rerunning a finished group script is cheap (< ~1–2 min each) but rarely needed;
  the aggregates in `agg/` let chart-only scripts render without re-streaming.
